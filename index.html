JSON vs JSON Schema

JSON (RFC 8259) : format d'échange texte. 6 types : object, array, string, number, boolean, null. Pas de commentaires, pas de dates natives, pas d'entiers/flottants distincts.

⚠️ JSON décrit une syntaxe, pas une structure attendue : rien n'empêche un champ manquant ou un mauvais type.

JSON Schema : le contrat vérifiable. 3 rôles :

  • Validation — rejeter les documents non conformes
  • Documentation — lisible par les humains et les outils
  • Génération — code, formulaires, données de test, complétion IDE

Anatomie d'un schéma

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://exemple.fr/schemas/produit.schema.json",
  "title": "Produit",
  "description": "Produit du catalogue",
  "type": "object"
}
  • $schema — dialecte utilisé (toujours l'expliciter)
  • $id — URI identifiant le schéma (base de résolution des $ref)
  • title / description — documentation
  • type — type attendu à la racine. Un schéma peut être un booléen : true = tout accepter, false = tout rejeter.

Convention de nommage : *.schema.json — et un $id stable dès que le schéma est partagé.

Le mot-clé type

  • integer n'est pas un type JSON : c'est une contrainte ajoutée par JSON Schema (ex. 1.0 est accepté comme entier)
  • type accepte un tableau : { "type": ["string", "null"] } = nullable
  • Sans type, le schéma accepte n'importe quoi

Chaînes de caractères

{
  "type": "string",
  "minLength": 5,
  "maxLength": 5,
  "pattern": "^[0-9]{5}$"
}
  • minLength / maxLength — longueur
  • pattern — regex ECMA-262, non ancrée par défaut : il faut ^ et $ explicitement

⚠️ Sans ancrage, [0-9]{5} valide aussi "x87000y". Toujours borner maxLength sur les entrées externes.

Nombres

{
  "type": "number",
  "exclusiveMinimum": 0,
  "maximum": 20,
  "multipleOf": 0.5
}

minimum/maximum = bornes inclusives · exclusiveMinimum/exclusiveMaximum = exclusives · multipleOf = granularité.

Un montant, un âge ou une quantité sans bornes = erreur latente.

enum et const

{ "statut": { "enum": ["draft", "recommandation", "archive"] } }
{ "version": { "const": 2 } }
  • enum — valeur ∈ liste fermée (≥ 1 élément)
  • const — enum à une seule valeur ; comparaison structurelle stricte (égalité profonde)
  • const sert de discriminant dans les unions oneOf

Objets : properties vs required

properties

Associe un sous-schéma à chaque clé. Ne rend PAS les clés obligatoires ! Une clé absente est simplement... non validée.

{} → valide !

required

Tableau de clés qui doivent être présentes. Présence ≠ non-nullité : "nom": null satisfait required mais pas type: string.

{ "nom": null } → rejeté si type: string

Formule à retenir : « properties décrit, required impose. »

additionalProperties

{
  "type": "object",
  "properties": { "nom": { "type": "string" } },
  "required": ["nom"],
  "additionalProperties": false
}
  • Défaut : true — toute clé inconnue est acceptée
  • false — schéma fermé : clés inconnues rejetées
  • Ou un sous-schéma : { "additionalProperties": { "type": "string" } }

🔒 Enjeu de sécurité majeur : mass assignment. Ex. {"nom": "Ada", "isAdmin": true} passe si le schéma est ouvert !

Tableaux

{
  "type": "array",
  "items": { "type": "string", "minLength": 1 },
  "minItems": 1,
  "maxItems": 10,
  "uniqueItems": true
}
  • items — schéma appliqué à chaque élément
  • minItems / maxItems — taille ; borner maxItems sur toute entrée externe (vecteur de DoS)
  • uniqueItems — pas de doublons (égalité profonde)
  • contains + minContains/maxContains — au moins n éléments conformes

Qu'est-ce que XML ?

eXtensible Markup Language — recommandation W3C (1998), simplifiant SGML. Un méta-langage : il définit comment créer vos propres langages de balisage.

Format texte, auto-descriptif, indépendant de la langue et de la plateforme. Écosystème : XSD, XPath, XSLT, XQuery, SOAP, XHTML, SVG…

Anatomie d'un document

<?xml version="1.0" encoding="UTF-8"?>   <!-- prologue -->
<etudiants>                             <!-- racine (unique) -->
  <etudiant num="E42">                  <!-- élément + attribut -->
    <nom>Ada</nom>                      <!-- élément + texte -->
    <note>15.5</note>
  </etudiant>
</etudiants>

🌳 Un document XML EST un arbre : nœuds, parents, enfants — un seul parent par nœud. Pensons arbre, pas contenu textuel.

Règles de bonne formation (well-formed)

  1. Un unique élément racine
  2. Toute balise ouverte est fermée : <a>...</a> ou auto-fermante <a/>
  3. Imbrication stricte : <b><i>texte</i></b>, jamais <b><i>...</b></i>
  4. Valeurs d'attributs entre guillemets ou apostrophes
  5. Un attribut présent au plus une fois par élément
  6. Sensible à la casse : <Nom> ≠ <nom>

🚫 Un document mal formé est rejeté en bloc : pas de mode dégradé (contrairement à HTML).

Attribut ou élément ?

AttributÉlément
Métadonnée simple, atomiqueDonnée métier, structurée, texte long
Non répétableRépétition possible
Pas de structure ni d'ordreÉvolutif

Règle pragmatique : l'attribut qualifie, l'élément contient. En cas de doute → élément.

Entités et CDATA

5 entités prédéfinies : &lt; (<) · &gt; (>) · &amp; (&) · &quot; (") · &apos; (')

< et & sont toujours interdits dans le texte. Références de caractères : &#233; ou &#xE9; pour é.

<script><![CDATA[
if (a < b && c > d) { alert("brut, non analysé"); }
]]></script>

CDATA = bloc de texte non analysé, pratique pour du code ou du HTML embarqué. Les commentaires (<!-- -->) ne sont pas des données : certains analyseurs les ignorent.

Encodage

  • UTF-8 par défaut et recommandé, déclaré explicitement
  • Erreur classique : fichier en ISO-8859-1 déclaré UTF-8 (ou l'inverse) → caractères corrompus
  • BOM UTF-8 toléré ; UTF-16 détecté via le BOM
  • standalone="yes" : pas de dépendance externe

⚠️ L'encodage déclaré doit refléter l'encodage réel des octets : source n°1 d'erreurs liées aux accents.

✅ Valide implique bien formé, pas l'inverse. La validation est un choix.

Le problème des collisions

XML encourage à combiner des vocabulaires (SOAP + métier, XHTML + SVG…). Que signifie <titre> quand deux vocabulaires le définissent ?

<bibliotheque>
  <livre>
    <titre>Dune</titre>     <!-- œuvre -->
    <auteur>
      <nom>Herbert</nom>
      <titre>Dr</titre>   <!-- civilité ! -->
    </auteur>
  </livre>
</bibliotheque>

Solution : Namespaces in XML (1999) — qualifier chaque nom par un URI. Comme on ne peut pas écrire une URI dans un nom de balise (le « / » est interdit), on utilise un préfixe = alias local de l'URI.

xmlns : déclaration, préfixes, portée

<biblio:livre
    xmlns:biblio="https://exemple.fr/ns/biblio"
    xmlns:pers="https://exemple.fr/ns/personne">
  <biblio:titre>Dune</biblio:titre>
  <pers:titre>Dr</pers:titre>
</biblio:livre>
  • Nom qualifié = (URI, nom local)
  • L'URI est un identifiant : rien n'est téléchargé, il n'a pas à être résolvable
  • Portée : l'élément porteur de la déclaration et ses descendants
  • Le préfixe est un alias local : seul l'URI compte pour l'égalité — deux documents avec des préfixes différents mais les mêmes URI sont équivalents

Espace de noms par défaut et attributs

<commande xmlns="https://exemple.fr/ns/vente" id="CMD-1">
  <ligne sku="ABC"/>
</commande>
  • xmlns="URI" (sans préfixe) = namespace par défaut pour les éléments non préfixés
  • xmlns="" annule le namespace par défaut dans un sous-arbre
  • id et sku n'appartiennent à aucun namespace

⚠️ Piège classique d'examen : le namespace par défaut ne s'applique jamais aux attributs non préfixés. Un attribut préfixé (ex. xsi:type) est, lui, pleinement qualifié.

Namespaces fréquents

  • http://www.w3.org/2001/XMLSchema (xs: ou xsd:) — le langage XSD
  • http://www.w3.org/2001/XMLSchema-instance (xsi:) — attributs côté document (xsi:type, xsi:nil)
  • http://schemas.xmlsoap.org/soap/envelope/ — SOAP 1.1
  • http://www.w3.org/1999/XSL/Transform (xsl:) — XSLT

⚠️ Piège XPath/DOM : un élément dans un namespace ne correspond pas à son nom local seul — il faut lier le préfixe dans l'outil aussi. Convention : URI stable versionnée (…/ns/vente/1.0), contrôlée par l'organisation.

Les pièges à graver dans le crâne

properties ne rend pas obligatoire. Une clé absente est simplement non validée. « properties décrit, required impose. »

required ≠ non-null. "nom": null satisfait required mais pas type: string.

additionalProperties = true par défaut. Schéma ouvert → mass assignment : {"isAdmin": true} passe.

pattern n'est pas ancré. Sans ^ et $, [0-9]{5} valide "x87000y".

JSON n'a pas de date native ni de distinction int/float. Pas de commentaires, pas d'entiers séparés des flottants.

Sans type, un schéma accepte n'importe quoi. Toujours le spécifier.

Bien formé ≠ valide. Un document mal formé est rejeté en bloc ; la validation XSD est un choix, pas une contrainte automatique.

Namespace par défaut ≠ attributs. xmlns="..." qualifie les éléments, jamais les attributs non préfixés.

L'URI d'un namespace est un identifiant, pas une URL. Rien n'est téléchargé, il n'a pas à être résolvable.

Borner les entrées externes. maxLength, maxItems, bornes numériques = protection contre ReDoS et DoS, pas juste de la politesse.

Règles d'or

✅ Validation aux frontières (API, files, fichiers) — échouer tôt et explicitement. L'erreur doit être rejetée à la frontière, pas se transformer en NPE au milieu du code.

✅ Un contrat utile est exigeant : requis par défaut, optionnel justifié.

✅ Même schéma, plusieurs frontières : un seul contrat réutilisé partout (API, Kafka, Mongo, config, formulaires) limite les problèmes.

✅ L'attribut qualifie, l'élément contient — en cas de doute, élément (plus évolutif).

JSON Schema : composition et réutilisation

$defs contient des définitions locales réutilisables avec $ref. allOf impose toutes les branches, anyOf au moins une, et oneOf exactement une. Utilise const comme discriminant pour des variantes exclusives.

{
  "$defs": { "Identifiant": { "type":"string", "pattern":"^[A-Z]{2}-[0-9]+$" } },
  "type":"object", "properties": { "id": { "$ref":"#/$defs/Identifiant" } }
}

Conditions, formats et objets extensibles

{
  "if": { "properties": { "pays": { "const":"FR" } } },
  "then": { "required":["numeroTVA"] },
  "else": { "required":["identifiantFiscal"] }
}

additionalProperties s'applique localement. En 2019-09/2020-12, unevaluatedProperties est utile après composition pour refuser les propriétés restées non évaluées. format documente ou vérifie selon le validateur (email, date-time, uri) : son support peut être configurable.

XSD : types, cardinalités et ordre

<xs:element name="ligne" minOccurs="1" maxOccurs="unbounded">
  <xs:complexType>
    <xs:sequence>
      <xs:element name="sku" type="xs:string"/>
      <xs:element name="quantite" type="xs:positiveInteger"/>
    </xs:sequence>
  </xs:complexType>
</xs:element>
  • simpleType : valeur sans éléments enfants ; complexType : structure, attributs et contenu.
  • sequence impose l'ordre ; choice choisit une branche ; all autorise chaque élément au plus une fois, dans n'importe quel ordre.
  • minOccurs/maxOccurs expriment les cardinalités (défaut : 1).
  • Facettes : minLength, maxLength, pattern, enumeration, minInclusive, totalDigits.
  • extension ajoute des champs à un type de base ; restriction le resserre.

DTD, XSD, XPath et outils Python

DTD est ancien et peu typé ; XSD est XML, typé, namespace-aware et exprime des contraintes riches. XPath navigue l'arbre avec des chemins et prédicats : /commande/ligne[@sku='ABC-123'], count(//ligne), ancestor::commande, following-sibling::ligne.

from lxml import etree
parser = etree.XMLParser(resolve_entities=False, no_network=True)
doc = etree.parse("commande.xml", parser)
print(doc.xpath("//c:ligne", namespaces={"c":"https://exemple.fr/ns/vente"}))

Sécurité à savoir expliquer

  • XXE : entités externes pouvant lire des fichiers ou appeler le réseau. Désactiver entités et réseau.
  • Billion Laughs : expansion d'entités qui sature mémoire/CPU.
  • Mass assignment : champs JSON inattendus injectés dans un objet métier. Allowlist + schéma fermé.
  • ReDoS / DoS : regex simples et limites de taille, profondeur, tableaux, propriétés et ressources.

OpenAPI 3.1 s'appuie sur JSON Schema 2020-12 : le contrat peut documenter l'API et piloter la validation, mais il faut vérifier le support de l'outil.

1. Sémantique JSON Schema 2020-12 : évaluations et composition

Les mots-clés de validation ne jouent pas tous le même rôle. Un applicator (par exemple allOf, if, properties) applique des sous-schémas et peut produire des annotations. En 2020-12, unevaluatedProperties exploite les propriétés évaluées par les branches applicables, contrairement à additionalProperties qui ne raisonne que localement dans son emplacement.

{
  "type": "object",
  "properties": {"kind": {"enum": ["student", "teacher"]}},
  "required": ["kind"],
  "oneOf": [
    {"properties": {"kind": {"const": "student"}, "level": {"enum": ["L1", "L2", "M1"]}}, "required": ["level"]},
    {"properties": {"kind": {"const": "teacher"}, "department": {"type": "string"}}, "required": ["department"]}
  ],
  "unevaluatedProperties": false
}

Piège : mettre additionalProperties:false dans le schéma racine avant les branches peut rejeter level et department avant que la composition ne les ait évaluées. Ici, unevaluatedProperties:false est le choix cohérent.

2. Récursivité, tuples et contraintes de tableaux

{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$defs": {"node": {"type":"object", "properties": {
    "value": {"type":"string"}, "children": {"type":"array", "items":{"$ref":"#/$defs/node"}}
  }, "required":["value"], "unevaluatedProperties":false}},
  "$ref":"#/$defs/node"
}
  • prefixItems décrit un tuple positionnel ; items contrôle les éléments restants.
  • contains impose la présence d’éléments correspondant à un sous-schéma ; avec minContains, on exprime “au moins n”.
  • Une récursion doit être bornée côté application : profondeur, taille totale et nombre de nœuds restent des limites opérationnelles.

3. XSD : namespaces, composition et identité

<xs:unique name="uniqueProductSerial">
  <xs:selector xpath="catalog/product"/>
  <xs:field xpath="@serial"/>
</xs:unique>
<xs:keyref name="orderProductExists" refer="productKey">
  <xs:selector xpath="order/product"/>
  <xs:field xpath="@serial"/>
</xs:keyref>

Lecture d’examen : unique interdit les doublons mais n’impose pas forcément la présence ; key impose une valeur existante et unique ; keyref impose une référence vers une clé déclarée. Les XPath des identity constraints sont relatifs au contexte de l’élément qui porte la contrainte.

Avec elementFormDefault="unqualified", les éléments locaux ne sont pas dans le namespace cible. Si un namespace par défaut est hérité dans le document, il faut parfois écrire xmlns="" pour réinitialiser la portée. Les attributs non préfixés, eux, restent sans namespace.

4. XPath namespace-aware et sécurité

ns = {"c": "https://exemple.fr/commande"}
doc.xpath("/c:commande/c:lignes/c:ligne[@quantite > 10]", namespaces=ns)
doc.xpath("count(//c:ligne)", namespaces=ns)

Un XPath ne “voit” pas un élément par son nom local si celui-ci est namespace-qualified. En Python, fournir explicitement le mapping préfixe → URI. Pour XML hostile : désactiver les entités externes, le réseau et les résolutions DTD, imposer des limites de taille/profondeur et traiter les erreurs comme des rejets de frontière.

Cas A — oneOf ou anyOf ?

Un paiement contient method:"card", last_digits et iban. Les deux branches autorisent leurs propriétés connues mais n’interdisent pas les propriétés inconnues. Pourquoi ce payload peut-il passer avec anyOf ? Quelle correction robuste proposes-tu ?

Avec anyOf, une seule branche valide suffit : la branche carte peut ignorer iban si elle n’est pas fermée. Utiliser oneOf avec discriminant const et fermer chaque branche (additionalProperties:false), ou composer soigneusement avec unevaluatedProperties:false.

Cas B — XSD namespace

La racine porte xmlns="urn:catalogue". Un XSD client déclare elementFormDefault="unqualified". Pourquoi les éléments locaux nom et email peuvent-ils devenir invalides ?

Ils héritent du namespace par défaut du document alors que le schéma attend des éléments locaux sans namespace. Il faut réinitialiser la portée sur l’élément client avec xmlns="" (sans changer la bonne formation XML).

Cas C — schéma vs métier

Le schéma impose total positif et une liste d’articles valide. Peut-il garantir que total = Σ(quantity × unit_price) et que chaque produit existe au catalogue ?

Pas raisonnablement avec JSON Schema seul : il valide surtout la forme. La somme et l’existence en base relèvent du service métier/transactionnel, après validation syntaxique et structurelle.

Cas D — threat model

Un endpoint accepte un XML de 40 Mo contenant une DTD externe et un JSON avec isAdmin:true. Donne quatre contrôles prioritaires.

Taille et profondeur bornées ; entités externes/DTD/réseau désactivés ; parseur durci contre expansion et SSRF ; schéma JSON fermé par allowlist, validation avant mapping objet, puis autorisation métier indépendante.
